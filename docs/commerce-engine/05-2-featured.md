# 5-2. 特集は同時に1件

## 動作

「トップの特集にする」を保存し、公開・更新すると、その記事を特集にする。
以前の特集は公開を続けたままfeaturedをfalseにする。
以前の記事の下書き側もfeaturedだけをfalseにし、本文や画像は変更しない。
下書きのrevisionは通常の更新と同じく増える。
下書きと公開版がそれまで一致していた場合はsource_revisionも合わせる。
未公開の編集がある場合は公開版へコピーせず、編集中の内容を保持する。

古いタブから以前の記事を保存・公開しようとすると、revision不一致で拒否する。
原稿一覧を更新して開き直せば特集チェックは外れている。
別の未公開下書きで予約していたチェックは維持し、その記事の公開時に切り替える。
特集のチェックを外して公開・更新した場合、特集は未指定になってよい。
特集を非公開にしたときも未指定になる。勝手に別の記事は選ばない。

公開・非公開処理は共通のトランザクションロックで順番に実行する。
DBの一意インデックスでも、公開版の特集が2件になることを防ぐ。
途中で失敗した場合は以前の特集を含めて処理全体を取り消す。

## 反映について

ローカルに新しいSQLを追加した段階では、会社DBはまだ変わらない。
supabase/migrations/20261112030000_single_featured.sql をGitHub連携で適用する。
既存データに複数の特集があれば、更新日時が新しい1件を残して整理する。
管理画面はDB上の現在の特集名を表示する。
トップページはまだdramas.jsのため、実際のサイト表示との接続は次工程。

## 確認

テスト記事Aを特集として公開→Bを特集として公開し、Aの公開版と下書きの
featuredがfalse、Bの公開版がtrueであることを確認する。
古いAのタブから更新が拒否され、開き直したAの通常更新でBを奪わないことを確認する。
Bの公開が失敗した場合にAの特集指定が残ることも確認する。
