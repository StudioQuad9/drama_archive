## 原稿と表示を分ける

| 原稿の項目 | 現在の項目 | 役割 |
| --- | --- | --- |
| slug | id | 記事URLに使う識別名 |
| type | 固定値 drama-review | 記事の種類 |
| content.title | title | 記事タイトル |
| content.heading | reviewTitle | レビューの見出し |
| content.body | review | Markdown本文 |
| content.bodyFormat | 固定値 markdown | 本文の保存形式 |
| metadata | 画像・評価・ジャンル等 | ドラマレビュー固有の付随情報 |
| publishedAt | publishedAt | 公開日時 |

現在の全項目を往復変換できる形にする。画像・配列はコピーし、変換後の
編集が既存データを直接書き換えないようにする。
本文には色・余白・用紙サイズなどを保存しない。見出し・段落・リスト等の
意味をMarkdownで保存し、Web用と将来のVivliostyle用の装飾を別途適用する。
YouTube動画のようなWeb向け情報のPDFでの扱いは、PDF出力段階で決める。

## 次に実装するDB構造の案

- articles：記事の固定ID、所有する管理者、作業中原稿、更新日時。
- article_publications：公開した原稿のコピー、公開用slug、公開日時。

作業中原稿は content と metadata を保存する。公開版にも同じ構造を使う。
公開用slugは重複不可とし、公開済みURLの変更は別途明示的に扱う。
下書き保存は articles のみ更新する。公開操作時だけ公開用データを
まとめて更新し、途中の状態が公開されないようDBの一連の処理として扱う。
非公開化は公開用データを取り除き、作業中原稿は残す。
公開履歴の保持は将来の拡張とし、最初は現在の公開版のみを保存する。

一般訪問者は公開用データだけを読み取れるようにする。
作業中原稿の読み書きと公開操作は、許可した管理者のみに制限する。
ログインできたことだけで管理者とは判定しない。
この制限は画面だけでなく、SupabaseのDB側にも設定する。
変換処理自体には認証・アクセス制限の役割を持たせない。

## 実装の順序

1. 原稿形式の確認（今回）。
2. CommerceEngineプロジェクト作成、DBとアクセス制限の追加。
3. 公開データの読み込みと既存カード表示への接続。
4. 管理者ログインと記事管理画面。
5. 下書き保存・公開・非公開化の動作確認。

会社Vercelで現在のサイトを表示する作業は、接続先と公開ブランチを
確認したうえで早期に行う。既存の就活サイトとは別プロジェクトにする。
