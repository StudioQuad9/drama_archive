# 1-2. 下書きの作成・編集・保存

対応コミット：`5f8d892` — ログイン機能と原稿執筆の最低限の機能を実装する

## 今回の変更と対象

ローカルの /admin に保存済み原稿一覧と入力フォームを追加した。
DB構造・公開サイトは変更していない。GitHubへの送信も別の段階で行う。

- AdminAccess.jsx：ログイン・管理者確認。確認後に原稿画面を表示する。
- DraftWorkspace.jsx：原稿一覧、タイトル・レビュー見出し・本文の入力と保存。
- admin.module.scss：管理画面の見た目。

## 保存の流れ

新規作成では articles に1件追加する。slugは draft- にランダムな識別子を
付けて生成する。公開用URLの指定、画像・評価などの入力は次の段階で実装する。
本文はMarkdown文字列として保存し、装飾を埋め込まない。
タイトルや本文が空でも下書きは保存できる。

既存原稿はIDと読み込み時のrevisionを条件にcontentだけを更新する。
metadata・所有者などは変更しない。revisionはDBのトリガーで自動更新される。
別タブで更新済みなら一致する行がなく、上書きせず再読み込みを案内する。
article_publicationsには書き込まない。公開の操作もまだない。

一覧は本人の原稿を更新順で最大100件表示する。取得失敗と0件を区別する。
入力中は別原稿への移動、ログアウト、公開サイトへの移動で確認する。
ページを閉じる際もブラウザの確認を使う。自動保存・復元はまだないため、
通信失敗時は入力を画面に残し、必要ならコピーして保管する。
保存結果が通信の問題で不明な場合、新規追加の再試行で重複する可能性がある。
一覧を更新して既存の保存結果を確かめてから再試行する。

## ログイン状態の更新

トークン更新のたびに原稿画面を一旦消すと未保存入力が失われるので、
再確認中も現在の画面を保つ。権限の確認結果が変わったら表示を切り替える。
ユーザーが変わった場合はユーザーIDをキーに原稿画面を作り直す。
データへのアクセス制限は引き続きSupabase側のRLSが担う。

## 実際のSupabaseでの確認

1. /admin にログインし、テスト用のタイトル・見出し・本文を入力する。
2. 下書き保存を押し、保存完了の案内と一覧への追加を確認する。
3. 再読み込み後、一覧からその原稿を開き、文章が残っていることを確認する。
4. 本文を変更して保存し、同じ原稿が更新されることを確認する。
5. 2つのタブで同じ原稿を開き、片方で保存後、古い方の保存が拒否されることを確認する。
6. 未保存のまま原稿を切り替える操作で確認が出ることを確認する。
7. Supabaseのarticlesに保存され、article_publicationsは空のままであることを確認する。

管理者のパスワードやトークンはコード・文書に残さない。
